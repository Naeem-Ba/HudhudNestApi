لا يوجد "كود" هنا، بل إجراء. نفّذه بهذا الترتيب بالضبط لأن الرسالتين نفسيهما تحذران من

```powershell
git commit -m "Phase 2: unified error handling, validation, session error UX"

# إن كانت تغييرات Phase 3 موجودة في نفس working tree فوق تغييرات Phase 2،
# افصلها بعناية — git status سيوضح إن كانت الملفات متداخلة
```


**نقطة حرجة:** كلا التقريرين يذكران أن تغييرات Phase 3 على فرع منفصل
(`feature/phase3-search-filters-pagination`) عن Phase 2. إن كانت working tree الحالية
تخلط الاثنين معًا فعليًا (لا على فروع منفصلة فعلاً كما يوحي التقرير)، **لا تلتزم
الاثنين في نفس commit** — افصل الملفات يدويًا بالاستعانة بجداول "Changes Made" في كل
تقرير (تسرد أسماء الملفات بدقة)، أو استخدم `git add <files-من-Phase-2-فقط>` ثم
`git commit`، ثم كرر لـ Phase 3.

بعد الالتزام: **ادفع (push) إلى remote فورًا**. commit محلي بلا push ما زال عرضة لفقدان
القرص نفسه.

### 2. تفعيل فحص كلمة المرور المخترقة عند إعادة التعيين

الحل: إضافة نفس استدعاء `IPasswordSecurityService.ValidatePasswordAsync` المستخدَم في
`RegisterCommandValidator` إلى `ResetPasswordCommandValidator`. يحتاج الـ validator أن
يصبح async-aware عبر حقن الخدمة، تمامًا كما في `RegisterCommand.cs`.

```csharp
// HudhudNestApi.Application/Auth/Commands/ResetPassword/ResetPasswordCommand.cs

public sealed class ResetPasswordCommandValidator
    : AbstractValidator<ResetPasswordCommand>
{
    private readonly IPasswordSecurityService _passwordSecurityService;

    public ResetPasswordCommandValidator(
        IPasswordSecurityService passwordSecurityService)
    {
        _passwordSecurityService = passwordSecurityService;

        RuleFor(x => x.Email)
            .NotEmpty()
            .MaximumLength(320)
            .EmailAddress();

        RuleFor(x => x.Token)
            .NotEmpty();

        RuleFor(x => x.NewPassword)
            .NotEmpty()
            .WithMessage("Password is required.")
            .MinimumLength(8)
            .WithMessage("Password must be at least 8 characters long.")
            .CustomAsync(ValidatePasswordSecurityAsync);   // <-- الإضافة

        RuleFor(x => x.ConfirmPassword)
            .Equal(x => x.NewPassword);
    }

    // انسخ هذه الدالة بالضبط كما هي في RegisterCommandValidator —
    // نفس الأكواد الثابتة (error codes)، نفس سلوك الرسائل، صفر تكرار منطق جديد.
    private async Task ValidatePasswordSecurityAsync(
        string password,
        ValidationContext<ResetPasswordCommand> context,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrEmpty(password))
        {
            return;
        }

        var result = await _passwordSecurityService.ValidatePasswordAsync(
            password,
            cancellationToken);

        if (result.IsValid)
        {
            return;
        }

        foreach (var error in result.Errors)
        {
            context.AddFailure(new ValidationFailure(
                nameof(ResetPasswordCommand.NewPassword),
                error.Message)
            {
                ErrorCode = error.Code
            });
        }
    }
}
```

**تنبيه واحد مهم قبل أن تطبّق هذا حرفيًا:** لم أفحص هذه الجلسة ما إذا كان هناك مسار
منفصل لـ **تغيير كلمة المرور** (Change Password، لا Reset) بمُدخِل/validator خاص به —
إن وُجد، طبّق نفس التعديل عليه أيضًا؛ ابحث عن `ChangePasswordCommand` في
`HudhudNestApi.Application/Auth/Commands/` للتأكد.

**اختبار يستحق الإضافة فورًا** (نفس نمط الاختبارات الموجودة في المشروع):

```csharp
[Fact]
public async Task Should_Reject_Breached_Password_On_Reset()
{
    var command = new ResetPasswordCommand(
        Email: "user@example.com",
        Token: "valid-token",
        NewPassword: "Password123!",   // معروفة في قوائم التسريبات العامة
        ConfirmPassword: "Password123!");

    var result = await _validator.ValidateAsync(command);

    result.IsValid.Should().BeFalse();
    result.Errors.Should().Contain(e => e.ErrorCode == "PASSWORD_BREACHED");
}
```

### 3. إصلاح CORS في Staging

لم أستطع الوصول إلى بيئة Staging نفسها هذه الجلسة (لا وصول شبكي من هنا لأي نشر حي)،
لذا هذا الحل إجرائي لا كودي بالكامل — تحقّق من هذه النقاط بالترتيب على إعداد Staging
الفعلي:

1. **افحص القيمة الفعلية المنشورة** لـ `Cors:AllowedOrigins` في بيئة Staging (متغير بيئة
   أو `appsettings.Staging.json` إن وُجد) — تأكد أنها تطابق **نطاق الواجهة المنشورة
   فعليًا في Staging**، حرفًا بحرف (بلا `/` زائدة في النهاية، بروتوكول `https` لا
   `http`).
2. راجع `HudhudNestApi/Configuration/CorsRegistration.cs` للتأكد أن السياسة المسجَّلة
   تُطبَّق فعلًا على كل الـ endpoints التي يستدعيها الفرونت اند من Staging (وليس فقط
   على بعضها).
3. تحقّق تنفيذي وحيد يُثبت الإغلاق: افتح Staging من متصفح حقيقي، افتح Network tab،
   نفّذ أي طلب POST من الواجهة، وتأكد أن استجابة الـ preflight (`OPTIONS`) تحمل
   `Access-Control-Allow-Origin` مطابقًا تمامًا لأصل الواجهة — لا نجمة `*` (لن تعمل مع
   `withCredentials: true` أصلًا).

### 6. فهارس قاعدة البيانات المفقودة + pg_trgm

**لا تضِف فهرسًا بلا دليل** — هذا نص التزام المشروع نفسه في
`docs/performance/postgresql-query-analysis.md` (يذكره تقرير Phase 3 صراحة). لكن هنا
migration جاهزة تتبع نفس النمط المستخدَم مسبقًا في المشروع لأعمدة `City`/`Region`:

```csharp
// HudhudNestApi.Infrastructure/Migrations/{timestamp}_AddPropertyRangeFilterIndexes.cs
public partial class AddPropertyRangeFilterIndexes : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateIndex(
            name: "IX_Properties_Rooms",
            table: "Properties",
            column: "Rooms");

        migrationBuilder.CreateIndex(
            name: "IX_Properties_ColdRent",
            table: "Properties",
            column: "ColdRent");

        migrationBuilder.CreateIndex(
            name: "IX_Properties_WarmRent",
            table: "Properties",
            column: "WarmRent");

        migrationBuilder.CreateIndex(
            name: "IX_Properties_PurchasePrice",
            table: "Properties",
            column: "PurchasePrice");

        // نفس فهرس pg_trgm الموجود مسبقًا على City/Region — طبّقه على Title/Description
        migrationBuilder.Sql(
            "CREATE EXTENSION IF NOT EXISTS pg_trgm;");
        migrationBuilder.Sql(
            "CREATE INDEX IX_Properties_Title_Trgm ON \"Properties\" " +
            "USING gin (\"Title\" gin_trgm_ops);");
        migrationBuilder.Sql(
            "CREATE INDEX IX_Properties_Description_Trgm ON \"Properties\" " +
            "USING gin (\"Description\" gin_trgm_ops);");
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropIndex("IX_Properties_Rooms", "Properties");
        migrationBuilder.DropIndex("IX_Properties_ColdRent", "Properties");
        migrationBuilder.DropIndex("IX_Properties_WarmRent", "Properties");
        migrationBuilder.DropIndex("IX_Properties_PurchasePrice", "Properties");
        migrationBuilder.Sql("DROP INDEX IF EXISTS \"IX_Properties_Title_Trgm\";");
        migrationBuilder.Sql("DROP INDEX IF EXISTS \"IX_Properties_Description_Trgm\";");
    }
}
```

**قبل تطبيقها فعليًا في Production:** اتبع إجراء المشروع نفسه — نفّذها على نسخة تجريبية
(disposable) من قاعدة البيانات، وقِس `EXPLAIN ANALYZE` قبل/بعد على استعلام فلترة حقيقي
لكل عمود، ثلاث مرات، كما يشترط `postgresql-query-analysis.md`. لا تنشرها بلا هذا
الدليل — هذا بالضبط ما ميّز نهج المشروع حتى الآن (رفض فهرسة تخمينية).

### 9. إضافة `NameDe` لكيانات المواقع الجغرافية

```csharp
// HudhudNestApi.Domain/Lookups/Entities/Governorate.cs (ونفس النمط لـ District وNeighborhood)
public sealed class Governorate : BaseEntity
{
    public string NameAr { get; private set; } = string.Empty;
    public string NameEn { get; private set; } = string.Empty;
    public string NameDe { get; private set; } = string.Empty;   // <-- الإضافة

    // حدِّث Create()/الطرق الأخرى المقابلة لتقبل الاسم الألماني كمعامل اختياري
    // يبدأ بقيمة تساوي NameEn افتراضيًا (fallback أفضل من نص فارغ) حتى تُترجَم البيانات:
    public static Governorate Create(string nameAr, string nameEn, string? nameDe = null)
    {
        var entity = new Governorate
        {
            NameAr = nameAr,
            NameEn = nameEn,
            NameDe = nameDe ?? nameEn
        };
        return entity;
    }
}
```

### 10. تحقّق من تطابق التسلسل الجغرافي عند الكتابة

أضِف قاعدة `MustAsync` في validator إنشاء/تعديل العقار (ابحث عن اسمه الدقيق تحت
`HudhudNestApi.Application/Properties/Validators/`):

```csharp
RuleFor(x => x)
    .MustAsync(async (dto, ct) =>
    {
        if (dto.DistrictId is null) return true;   // لا تسلسل مطلوب إن لم يُحدَّد حي

        var district = await _lookupRepository.GetDistrictByIdAsync(dto.DistrictId.Value, ct);
        return district is not null && district.GovernorateId == dto.GovernorateId;
    })
    .WithMessage("District does not belong to the selected Governorate.")
    .WithErrorCode("DISTRICT_GOVERNORATE_MISMATCH");
```

(الاسم الدقيق للـ repository/interface يحتاج تأكيدًا من `HudhudNestApi.Domain/Lookups/`
— النمط أعلاه صحيح معماريًا بناءً على بقية المشروع، لكن لم أقرأ الملف الحقيقي لهذا
الـ validator تحديدًا هذه الجلسة.)
