### Local restores (all PASS)

1. **Baseline drill** — backup → restore into `hudhudnest_restore_drill` → SQL validation (83 PK, 119 FK, 36 unique
   indexes, no orphans, sequences OK, PostGIS 3.5.2 distance probe 130.35 m) → .NET `AppDbContext` verifier
   (no pending migrations) → API ready + read smoke → teardown. `restore-drill-evidence.json`: restore 7 s,

2. **Extended drill** — real Migrator (64 migrations) + 3 000 properties/400 users/1 500 images. Fingerprint of
   every table in `public` before backup and after restore:
   `INTEGRITY: PASS - 83 tables, 14075 rows, count+md5 identical for every table`; `SEQUENCES: identical (10)`.
   A canary row written to the source *after* the backup was **absent** from the restore (0 rows) — a direct
   demonstration of the RPO data-loss window.
3. **Failure handling** (same drill):
   - wrong key → `gpg: decryption failed: Bad session key`
   - one byte overwritten → `ERROR: Encrypted archive checksum mismatch.`
   - restore target on the production host → `ERROR: Restore target is on the production PostgreSQL server. This is forbidden.`
   - target name without `restore_drill` → `ERROR: Disposable target database name must contain restore_drill.`
4. **Migration recovery drill**:
   - head (64) → `dotnet ef database update 20260927104507_AddSocialPublicationLease` (Down works) → fingerprint → **pre-deploy backup**
   - deploy: Migrator applies the newest migration (history 63 → 64)
   - disaster: delete 750 `Properties` + all `PropertyImages` (damaged DB left untouched)
   - restore into a *new* DB: history 63, `INTEGRITY vs pre-deploy state: PASS (83 tables identical)`; 8 s
   - forward: Migrator re-applies migration 64 on the restored DB; `Properties=1500 PropertyImages=750` (full data back)
5. **Failed migration** (throwaway copy of the repo with a migration that does `CREATE TABLE`, `ALTER TABLE`, then
   `SELECT 1/0`): Migrator exit 1, `division by zero`, history stays at 64, **no** `drill_partial_marker` table,

Rollback of the *application* (Render): `scripts/deployment/rollback-application.sh` guards exercised —
missing env, unconfirmed auto-deploy pause, non-HTTPS URL, malformed deploy id all refuse; a bogus key
reaches Render and gets `401`. **No real rollback was executed.**

## 4. RPO / RTO

| | Stated (`rpo-rto.md`) | Measured | Observed in production |
|---|---|---|---|
| RPO | 24 h | canary written after backup is lost, nothing before it is | gaps of 49–75 h in the last 5 weeks |
| RTO | 120 min | 5.3 min end-to-end (baseline drill), 8–15 s for the restore itself | unknown |

Honest limits of the RTO number: the datasets are tiny (≈0.5 MB archive, 14 k rows). Add for a real incident:
object-store download, provisioning a new Supabase/Postgres instance, secret/connection-string swap and deploy,
DNS/TLS. Restore time grows roughly linearly with data size; **re-measure against a production-size backup
before quoting an RTO to anyone.** Also note `scripts/database/*` still default to a 60-minute RPO
(`RPO_TARGET_SECONDS=3600`), while CI passes 90 000 s and `rpo-rto.md` says 24 h — three different numbers.

## 7. RUNBOOK

### A. Prove production restorability (do this first)

```bash
gh workflow run database-restore-drill.yml --repo Naeem-Ba/HudhudNestApi -f fresh_backup=false
gh run watch --repo Naeem-Ba/HudhudNestApi
```

Success = job green and `restore-drill-evidence.json` shows `result: passed`, with a non-zero
`downloadDurationSeconds`. Needs Actions budget and artifact quota to be available.

### B. Local rehearsal (any machine with Docker + .NET 8 SDK)

```bash
bash scripts/database/run-local-restore-drill.sh        # ~5 min once images are built
```

On Windows checkouts older than the `.gitattributes` fix, first run `sed -i 's/\r$//' scripts/database/critical-tables.txt`.

### C. Incident (database lost or corrupted)

1. Declare incident, UTC start, owner. Pause Render auto-deploy. Do **not** write to the damaged DB.
2. Pick the newest manifest inside RPO: `bash scripts/database/download-latest-backup.sh`.
3. `bash scripts/database/verify-backup.sh` — checksum, decrypt, TOC. On failure take the previous backup.
4. Provision a **new** PostgreSQL 17 + PostGIS database (never restore over the damaged one).
5. `bash scripts/database/restore-postgres.sh` with `RESTORE_TARGET_ENVIRONMENT=recovery-drill`,
   `RESTORE_TARGET_DISPOSABLE=true`, `ALLOW_DESTRUCTIVE_RESTORE=true` and `PRODUCTION_DATABASE_URL` set so the
   host guard is active. (Target name must contain `restore_drill`; for a real cut-over, restore into a drill-named
   database and then rename it or repoint the connection string after verification.)
6. `bash scripts/database/verify-restored-database.sh`, then run the fingerprint compare if you still have the source.
7. Run `HudhudNestApi.Migrator` against the restored DB (applies anything newer than the backup).
8. Point `ConnectionStrings__DefaultConnection` at the restored DB, deploy / roll back app
   (`scripts/deployment/rollback-application.sh` or the protected workflow), check `/health/ready` and a read.
9. Record RPO (time of last backup vs incident), RTO, backup id, approver.

### D. Bad migration

- Failed mid-way: EF rolled that migration back; keep the old app, fix forward, re-run Migrator. Verify with
  `select max("MigrationId") from "__EFMigrationsHistory"`.
- Completed but harmful: stop traffic, restore the **pre-deployment backup** into a new DB (procedure C),
  re-apply migrations forward after the fix. Always take and verify a backup before any release that contains a
  migration (the production gate already requires it).

### E. Failure handling quick table

| Symptom | Meaning | Action |
|---|---|---|
| `Encrypted archive checksum mismatch` | corrupted/tampered object | quarantine, use previous backup |
| `gpg: decryption failed` | wrong key | check key version; never print it |
| `Restore target is on the production PostgreSQL server` | guard working | fix the target URL |
| `Unsafe critical table name` | CRLF in `critical-tables.txt` | apply the `.gitattributes` fix / strip `\r` |
| Backup job "red" but log says uploaded | artifact quota | trust the bucket manifest, free quota |
| No run at all for > 26 h | scheduler/budget outage | treat as incident, run manually (`workflow_dispatch`) |
